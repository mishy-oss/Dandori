# Dandori

タスク・スケジュール管理アプリ。時間軸タイムライン、ステータス別ボード、月単位のタスク計画とバーンダウンを組み合わせた、iPhone 中心の個人用 local-first PWA。

アプリ本体は [dandori/](./dandori) にあります。

Googleログインによる本人の端末間タスク同期と、Googleカレンダーの双方向同期に対応しています。利用にはGoogle CloudとCloudflareの設定が必要です。手順と同期対象は [GOOGLE_SYNC.md](./GOOGLE_SYNC.md) を参照してください。未設定でも端末のみで利用できます。

ナビゲーションと見出し、フォームの項目・操作ボタン・説明文は日本語です。ナビゲーションは「予定 / ボード / 設定」を使います。タスク一覧はボードへ統合しました。種別・優先度・ステータスの選択肢は英語のままです。入力済みのタスク名やGitHubのコミットメッセージは元の内容を表示します。

## 月単位のタスク管理

- スプリントの作成・開始・完了操作は廃止し、1日から末日までのカレンダー月を選んで管理します。
- ボードで検索（タイトル・番号・ラベル）、優先度・種別の絞り込み、全月表示を利用できます。繰り返しは、いずれかの回が条件に一致すれば月内の各回をまとめて表示し、完了数や次の未完了を維持します。クリアは検索・優先度・種別を戻します。
- 通常カードの「対象月」、または繰り返しカードを展開した各回の「対象月」から別月へ移動できます。繰り返しは選んだ回だけが移動します。別月への移動時は元の時刻配置を解除します。全月表示中のステータス変更は所属月を保ち、並べ替えは対象月表示で行います。
- 月次バーンダウンはボード内で展開して確認できます。選択した対象月全体の集計で、検索・絞り込み・全月表示には連動しません。
- ステータスの件数は繰り返しをまとめたカード数です。一覧には選択列と全列のカード数、繰り返し各回を含むタスク数を分けて表示します。親とepicを除くバーンダウンの件数とは集計対象が異なります。
- 未完了タスクは、月が変わった後の起動・画面復帰・保存時に今月へ自動で繰り越します。起動したまま日付をまたぐ場合も更新します。予定日と開始時刻は勝手に変更しません。
- 繰り返しの予定は、今月と選択した月の範囲内で自動生成します。ボードでは同じ繰り返しを1枚へまとめます。
- 繰り返しタスクの編集では「この回のみ」（初期選択）と「この回以降」を選べます。「この回以降」は変更したタイトル・説明・ラベル・種別・優先度・期限・時刻・所要時間・通知設定を、後の未完了分と今後生成する回に反映します。変更していない項目は各回の設定を維持し、ステータス・親子関係・対象月は編集した回だけに反映します。
- 頻度・曜日・間隔・繰り返し終了日の変更は「この回以降」で行います。必要な回を再生成し、不要になった後の未完了分を取り消します。完了済み・持ち越し履歴・削除済みの回は保護し、子タスクや持ち越し元との関係がある回は単独タスクとして残します。曜日変更時は編集した回も指定日以降の最初の該当日へ配置します。「繰り返さない」を選ぶと編集した回を単発にし、後の未完了分を取り消します。
- 「この回のみ」の変更は将来の生成内容へ引き継ぎません。Googleカレンダー由来の繰り返し予定は従来どおり1回分のみ編集し、繰り返しルールはGoogle側で変更します。
- バーンダウンはEpicと子を持つ親を除いた作業タスクの件数で集計します。日別実績は変更適用後から記録し、記録開始前の履歴は作りません。過去月の記録は繰り越し後も残ります。
- 既存タスクは予定日、期限、作成日の順に対象月を補完し、未完了の過去月分は今月へ移します。旧スプリントの記録は互換用に保持します。「すべての月のタスクを表示」で過去や未来のタスクも検索できます。

## ラベル

- 作成・編集画面で既存ラベルを候補から選べます。入力すると部分一致で絞り込み、追加済みの候補は表示しません。候補が多い場合は候補欄をスクロールできます。新しいラベルは「追加」またはEnterで登録でき、入力途中のラベルもタスク保存時に追加します。
- 前後の空白・連続する空白・全角と半角・英字の大小文字の違いは同じラベルとして扱います。例えば`API`・`ＡＰＩ`・`api`は既存の表記へ揃え、1タスク内でも重複させません。カンマでラベルを分割せず、単語の間の空白も完全には取り除きません。
- 候補は同じプロジェクトの全月・完了済みタスクも対象にし、削除済みタスクと持ち越し前の配置履歴は除きます。同じラベルの表示名は最初に使われた表記を優先します。
- 過去の保存データは一括で書き換えません。ラベル付きの保存時に表記を揃え、ボードの検索でも上記の表記揺れを吸収します。「営業」と「営業会議」など意味の違う名前は別ラベルのままです。

## Recurring（会議などの固定予定）

- ボードと編集画面のステータス順は「To Do → In Progress → Recurring → Done」です。
- 作成・編集画面のステータスで「Recurring」を選び、日付・開始時刻・所要時間を設定します。定例会議なら繰り返し曜日も設定できます。単発の会議にも使えます。
- ボードでは専用の列に表示します。In ProgressのWIP上限はありません。予定の配置・時刻変更・未配置への変更でも専用列を保ちます。
- 完了するとDoneへ移り、完了を解除するとRecurringへ戻ります。繰り返しの次回分も専用列で生成します。通常タスクへ変える場合はTo DoやIn Progressを選びます。
- 更新後の初回起動時に既存データにも列を追加します。既存のタスクは自動分類しないため、必要なものを選んで変更してください。

## 未完了タスクの持ち越し

- 編集画面の「翌日以降へ持ち越す」、または予定画面の「過去の未完了」から操作できます。持ち越し先の日付・開始／終了時刻・所要時間を確認して保存します。時刻を空にすると未配置で引き継ぎます。
- 元の日時・タイトル・説明・未完了状態は配置履歴として固定し、持ち越し先を別レコードで作成します。元の配置を編集・削除・完了する操作はできません。ボードの一覧は最新分だけを表示し、「持ち越し履歴」から過去分を確認できます。
- バーンダウンは最新分だけを数えます。今日分を完了しても昨日分は未完了の記録として残り、保存済みの過去の日別集計も維持します。月またぎの自動繰り越しは持ち越し済みの履歴を対象にしません。
- タイトル・説明・ラベル・種別・優先度・期限・通知設定を引き継ぎます。未完了の子孫タスクも複製して親子関係をつなぎ直し、時刻は未配置にします。子に未来の日付がある場合はその日付を維持します。完了済みの子は元の側に残します。
- 繰り返しは選んだ回だけを引き継ぎ、持ち越し先にルールを複製しません。Google予定の紐付けも複製せず、持ち越し先を配置すると独立した予定として同期します。元のGoogle予定は移動せず、Dandoriの配置履歴は以後のGoogle側の編集・削除でも上書きしません。
- 持ち越しの関係は端末間同期・JSONバックアップに含まれます。複数端末が同じタスクを持ち越した場合も同じIDを使い、内容が異なる場合は既存の同期競合の選択画面で解決します。

## 親子タスク

- 子がある親のステータスは子の進捗から自動計算します。すべて未着手ならTo Do、一部が進行中または完了ならIn Progress、すべて完了ならDoneになります。孫から祖先にも反映し、親だけを変更しても子の進捗が優先されます。
- 月をまたいだ子も集計します。子の作成・親の付け替え・削除・予定の追加や解除でも再計算し、既存データは読み込み時に整合させます。子がなくなったタスクは手動管理に戻り、最後の状態を保持します。
- ボードには親の名前と子の完了件数を表示します。編集画面では子のタイトルや「親タスクを編集」から関連タスクを開けます。閉じると元の入力内容へ戻ります。
- 親の編集画面では子タスク横の「外す」、子の編集画面では「親を外す」で親子関係だけを解除できます。解除はその場で保存され、タスク本体・予定・子が持つ子タスクは残ります。他の編集中の項目は変更しません。親の進捗は残った子で再計算し、子がなくなった場合は最後の状態を保持して手動管理へ戻ります。

## アプリ更新時の変更内容

- 設定画面の右上にあるⓘボタンから、利用中のバージョンまでの最近の変更をリリースノートとして最大5件確認できます。GitHubへのリンクは表示しません。
- リリースノートと更新通知には、取得できたコミット日を日本時間で表示します。デプロイ日ではありません。日付が取得できない項目は本文だけを表示します。
- 「新しいバージョンがあります」の通知に、公開リポジトリ `mishy-oss/Dandori` のコミットメッセージの先頭行を最大5件表示します。マージ操作だけのコミットは除き、テキストのみ表示します。
- ビルド時のGitコミットSHAをアプリと `version.json` に記録します。更新通知時に最新版のSHAを取得し、GitHub REST APIで現在の版との差分を確認します。履歴が分岐・ロールバックした場合は、公開済みの版までの「最近の変更」として表示します。
- 公開APIを使うため、トークン設定は不要です。通信エラー・APIの利用制限・Git情報のないビルドでは変更内容を取得できない旨を表示し、更新ボタンはそのまま利用できます。
- この機能を含む版へ一度更新した後、次回以降の更新通知から表示します。コミットメッセージはGitHubに書いた内容が表示されます。

## PWA Push 通知

通知を使うには VAPID キーを生成し、`dandori/.dev.vars` に `VAPID_PUBLIC_KEY`、`VAPID_PRIVATE_KEY`、`VAPID_SUBJECT` を設定してください。ひな形は `dandori/.dev.vars.example` にあります。キーはリポジトリへコミットせず、Cloudflare では `wrangler secret put` で登録します。本番 Worker の更新は `cd dandori; npm run deploy` です。

Push 通知は HTTPS と通知許可が必要です。iPhone/iPad は iOS 16.4 以降で、Safari の共有メニューからホーム画面に追加した PWA を開き、設定画面の「PWA通知を有効にする」を押してください。タスク通知には日付・開始時刻と通知タイミングを設定します。サーバーには通知時刻とタスク名のみを送信します。

## 開発

```bash
cd dandori
npm install
npm run dev            # 開発サーバー
npm run build          # 型チェック + 本番ビルド
npm run preview        # ビルド結果の確認(Service Worker はここで動作)
npm run lint
npm test               # リポジトリ層のテスト(fake-indexeddb)
npm run generate-icons # public/icon.svg から PWA アイコンを再生成
```

Service Worker は開発サーバーでは無効です。オフライン動作は `build` → `preview` で確認します。

## Cloudflare Workers Builds の設定

GitHub 連携の自動ビルドでは、Cloudflare の Worker → Settings → Build で次を設定してください。

| 設定 | 値 |
| --- | --- |
| Root directory | `dandori` |
| Build command | `npm run build` |
| Deploy command | `npx wrangler deploy` |

依存関係と `package-lock.json` は `dandori/` にあります。リポジトリ直下の `package.json` はローカル操作用のコマンド転送のみです。Root directory がリポジトリ直下のままだと、ビルド環境に TypeScript がインストールされず、`tsc: not found` で失敗します。

Root directory を変更したら、Cloudflare で失敗したビルドを再実行してください。VAPID キーはビルド変数ではなく、デプロイ先 Worker の Secret に設定します。

### 作業ブランチのプレビュー

Cloudflare の「プレビューのベース」側も Root directory を `dandori`、Build command を `npm run build` に設定し、プレビューのデプロイコマンドには `npx wrangler preview` を使います。本番側のデプロイコマンドは `npx wrangler deploy` です。

`dandori/wrangler.jsonc` の `previews.durable_objects.bindings` に通知用の `PUSH_DEVICES` を定義しています。同じ Worker 内の `PushDevice` クラスを参照し、プレビューごとに専用の保存領域が作られます。本番の通知購読や予定は共有しません。

プレビューで通知も試す場合は、`dandori/` で以下を実行し、入力を求められたときにプレビュー用のVAPIDキーと `mailto:メールアドレス` を入力してください。秘密鍵を設定ファイルへ書かないでください。

```bash
npx wrangler preview base-config secret put VAPID_PUBLIC_KEY
npx wrangler preview base-config secret put VAPID_PRIVATE_KEY
npx wrangler preview base-config secret put VAPID_SUBJECT
```

ベースのSecretは、その後に新しく作成されるプレビューへ適用されます。すでに作成済みのプレビューには `npx wrangler preview secret put VAPID_PUBLIC_KEY --name <プレビュー名>` のように3項目を個別登録してください。通知を使用しないプレビューではVAPIDキーは不要で、通知設定画面には未設定と表示されます。

設定の変更を対象ブランチへ反映した後、Cloudflareで失敗したビルドを再実行してください。将来のブランチでも設定が引き継がれるよう、通常のマージ手順で `develop` と `main` にも取り込みます。

参考: [Cloudflare Previews の設定](https://developers.cloudflare.com/workers/previews/configuration/)、[Durable Objects の分離](https://developers.cloudflare.com/workers/previews/resources/#durable-objects)。
